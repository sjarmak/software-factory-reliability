# Campaign Coverage Report

The coverage report is the join of a cross-repository campaign: a reduction
over child dispositions, recomputed from the durable event record on every
run and never cached between runs. The pattern rationale is in
[cross-repo-campaigns](../patterns/cross-repo-campaigns.md); the event
vocabulary is in [semantic-conventions.md](semantic-conventions.md);
query 7 in [sample-queries.sql](sample-queries.sql) finds undispositioned
targets directly.

Two properties make the report trustworthy. First, it is generated by
rerunning discovery against current repository state, so targets that
appeared after the campaign started show up as undispositioned instead of
staying invisible. Second, "published" is decided by system-of-record
evidence (the `work.acknowledged` event and what it cites), never by a
child's status field; a closed child is a status signal, not an outcome
signal (local observation,
gascity2026:docs/design/software-factory-philosophy.md).

## Report format

Every report carries the campaign identity, the intent as a rerunnable
discovery predicate, the timestamp of the discovery pass that produced it,
and the repository revisions that pass observed. Then seven sections:

1. **Current targets.** Every target the fresh discovery pass found, with
   repository and the revision it was evaluated at. This list is recomputed
   each run; it is not the list of children ever spawned.
2. **Published.** Targets whose child has `publication.committed` with a
   matching `verification.completed` digest and a `work.acknowledged` citing
   system-of-record evidence. Each row shows `work_id`, `publication_id`,
   `artifact_digest`, and acknowledgement date.
3. **Blocked.** Targets parked fail-closed, each with its stated `reason`,
   named `owner`, and the date blocked. A blocked row with no owner is a
   report-generation error, not a valid disposition.
4. **Exempted.** Targets deliberately excluded, each with the `reason` from
   its `work.reconciled` exemption record and a review date after which the
   exemption must be reconfirmed.
5. **Stale work.** In-flight children whose stamped `base_revision` no
   longer matches the repository state the discovery pass observed. Stale
   children need replanning; their eventual artifacts would publish against
   a base that moved.
6. **Undispositioned targets.** Current targets with none of the above.
   Includes both children mid-pipeline and targets discovery found for the
   first time this run.
7. **Campaign state.** One of `open` (undispositioned or stale rows exist),
   `blocked` (no undispositioned or stale rows, at least one blocked row),
   or `complete` (every current target published or exempted). Completion
   is a statement about the revisions this pass observed, at the time it
   ran, and a later discovery pass can reopen it.

## Worked example

Fixture: [multi-repo-api-migration](../fixtures/multi-repo-api-migration/).
Campaign `cmp-apimig-01`: migrate every hand-written caller of the
service-api v1 REST endpoints to the v2 client. The v2 interface shipped in
the `service-api` repository, which is the campaign's origin, not a target;
discovery scans the other four repositories for v1 call sites. The JSONL
sample stream in [sample-events.jsonl](sample-events.jsonl) contains the
client-go and cli child events from this campaign.

```
Campaign:   cmp-apimig-01
Intent:     no hand-written v1 service-api call sites outside service-api
Discovery:  2026-08-08T06:00:00Z
Origin:     service-api @ 7e6f5a4b3c2d (v2 client available since 2026-08-01)

Current targets (discovery pass of 2026-08-08):
  client-go   @ 8f7e6d5c4b3a
  client-js   @ 2a3b4c5d6e7f
  cli         @ 9a8b7c6d5e4f
  web         @ 6c5d4e3f2a1b

Published (2 of 4):
  client-go   wi-2101  pub-3320  sha256:4b8e...d8e6b  acknowledged 2026-08-06
  client-js   wi-2103  pub-3327  sha256:c1a9...44f2e  acknowledged 2026-08-07

Blocked (1 of 4):
  cli         wi-2102  since 2026-08-06  owner: platform-team
              reason: downstream batch API is incompatible with the v2
              client; migration cannot proceed until platform-team ships
              the compatible endpoint

Exempted (1 of 4):
  web         wi-2104  exempted 2026-08-07  review by 2026-09-30
              reason: web's hand-written calls are scheduled for
              replacement by a generated v2 client in September 2026;
              migrating them now would produce work discarded within weeks

Stale work:            none
Undispositioned:       none

Campaign state: BLOCKED
  2 published, 1 blocked, 1 exempted, 0 stale, 0 undispositioned.
  Not complete: cli lacks a published or exempted disposition. The block
  is owned by platform-team and surfaces in their escalation lane. The
  web exemption expires 2026-09-30 and reverts to undispositioned if not
  reconfirmed. The next completion check reruns discovery; if a new v1
  call site lands in any repository before then, it appears as an
  undispositioned target and moves the campaign back to OPEN.
```

## Generation notes

The report derives from the event store plus a fresh discovery pass; it
holds no state of its own. A cached report drifts the way any
watch-by-remembering layer drifts, silently (local observation,
gascity2026:docs/design/software-factory-philosophy.md). The failure
modes this format exists to surface, targets appearing after discovery and
bases moving under in-flight children, are exercised by the
[campaign-coverage-drifts](../drills/campaign-coverage-drifts/) and
[repository-base-moves](../drills/repository-base-moves/) drills.

Disposition counts must always sum: published + blocked + exempted + stale +
undispositioned = current targets. A report whose rows do not sum is
double-counting a target or, worse, dropping one, and the generator must
fail loudly rather than emit it. The blocked and exempted sections exist to
keep the campaign honest about incompleteness; a campaign owner reading only
the published count sees progress, and only the full reduction shows whether
the intent is actually satisfied everywhere it applies.
